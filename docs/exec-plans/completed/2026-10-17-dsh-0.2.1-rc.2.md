# Plan: Validate the DeepSeek reviewer on dsh 0.2.1-rc.2

_Drafted by Claude for Yang Hu, 2026-10-17. The user chose "upgrade and adapt claudex-loop" and authorized this plan, its claudex-loop review and the build._

## Goal

`--provider deepseek` review and inspection keep working on the globally installed dsh **0.2.1-rc.2**, with the same read-only guarantees as on 0.2.0-rc.2, and the version is recorded as validated.

Today every DeepSeek run on 0.2.1-rc.2 is refused or fails, for three reasons:
1. The version gate: `VALIDATED_DSH_CLI` is `("0.2.0-rc.2",)`.
2. The plugin allowlist: the new version enables plugins the allowlist does not know.
3. Credentials: headless no longer reads dsh's own store, so the run fails with `MISSING_CREDENTIAL`.

## Verified facts (spike, 2026-10-17, dsh 0.2.1-rc.2)

Each fact comes from `--dump-config` diffs against 0.2.0-rc.2 and from live keyless runs in disposable repos.

- [x] The CLI surface is unchanged: `--profile headless [--json] [--session-id] [task|-]`. The NDJSON event types are unchanged too (`session`, `status`, `tool_call`, `tool_result`, `final`, `error`).
- [x] The headless profile now patches `authorization`, `deepseek-account` and **`credentials`** to `disabled: true`. A keyless run (`env -u DEEPSEEK_API_KEY`) ends with `MISSING_CREDENTIAL`, even though `~/.dsh/.credentials.yaml` holds a valid key.
- [x] A patch entry `- id: credentials\n  disabled: false` restores store-based authentication: the keyless run exits 0 with `final` "OK". The runner still never reads the key.
- [x] New plugins enabled in headless:
  - `remote-access`: Remote method access control, a service;
  - `working-directory`: per-session cwd, a service;
  - `tool-working-directory`: a model-facing `working_directory` tool that can `cd`;
  - `web-deepseek-api`: a web provider.
- [x] Disabling the services `working-directory` or `remote-access` leaves 7 entries pending (`tool-fs`, `tool-fs-search`, `typert-gateway`, …). dsh prints `did not activate` and the model sees no tools. So both services must stay enabled, and the existing patch-warning guard already fails such a run closed.
- [x] With `tool-working-directory` and `web-deepseek-api` disabled, `credentials` enabled, and the existing `DSH_DISABLE` list, the model reports exactly `edit, glob, grep, read, read_image, write`. That is the same set as on 0.2.0-rc.2.
  - Under `read-only` a `write` is denied, and the escalation request is auto-denied ("no approval channel").
  - No file was created.
  - The enabled set minus the allowlist is `{remote-access, working-directory}`.
- [x] `tool-working-directory` must be disabled, not only audited. After a `cd`, relative `read`/`glob`/`grep` paths would resolve against the new directory, while the audit resolves them against the repository, so a confinement check could pass for an outside read.
- [x] `remote-access` in headless opens no listener. During a live reviewer run, `lsof` on the dsh process and its children showed one outbound TCP connection (DeepSeek API, :443), no LISTEN socket and no named unix socket. Its dump-config block carries no config (review F4).
- [x] `--dump-config` writes the unknown-id warning to stderr (`dsh: [<patch>] patch: entry "<id>" not found`). It does **not** write `did not activate`: a patch that disables the required `working-directory` service gives empty dump-config stderr, so that warning is runtime-only (review F7).
- [x] An unknown patch id prints `patch: entry "<id>" not found`. The new disable ids therefore make the patch invalid on 0.2.0-rc.2, and the existing guard fails such a run closed.
- [x] Neither change widens a workspace-write sandbox. In the agentic-os probe, `cd $HOME` followed by a write was denied under workspace-write. Writes to `/tmp` succeed in both versions, because `/tmp` is a standard writable temp root and not a regression. Reviews run `read-only` anyway.

## Decisions

These describe the design; every action is a checkbox under Progress Checklist.

1. **Support exactly 0.2.1-rc.2.** 0.2.0-rc.2 is dropped:
   - the globally installed binary is the new one;
   - the new patch ids are invalid on the old version.

   A version-conditional patch is not worth its complexity. An older version run with `--allow-unvalidated-cli` fails closed on the patch warning.
2. **Credentials come from dsh's own store, re-enabled by the patch.** The key lives only in dsh (`dsh web` Models page); `DEEPSEEK_API_KEY` in the launching environment still works. The runner never reads, writes or logs a key.
3. **Disable the new model-facing plugins:** `tool-working-directory` (cd tool) and `web-deepseek-api` (web provider).
4. **Allowlist the new services and drop the vendor-disabled entries.**
   - `remote-access` and `working-directory` expose no model tool and are required by `tool-fs`, `tool-fs-search` and `typert-gateway`.
   - `authorization` and `deepseek-account` are now disabled by the vendor in headless. An overlay that re-enables them should refuse.
5. **DeepSeek never resumes a session (review R1).**
   - In 0.2.1-rc.2, `dsh-working-directory` persists `working-directory/change` events in the session, and `dsh-tool-fs` resolves relative paths against that effective directory.
   - A reviewer session reopened in ordinary dsh (for example `dsh web`) and moved with `cd` would therefore carry the outside directory into a runner resume. `assertAdoptable` checks only the header cwd, and the audit resolves relative paths against the repository.
   - The runner therefore refuses `--resume` when the provider is `deepseek`. Every DeepSeek round, review or inspection, starts a fresh session in the repository, and the coordinator carries the prior findings and dispositions in `--feedback`.
   - This deletes a code path instead of verifying zstd session state. Inspections were already fresh-only.
6. **Fail closed before launch on patch warnings (review F3, F7).** `dsh_check_config` also refuses when `--dump-config` stderr contains `patch: entry`, so a renamed or missing plugin id stops the run before any content reaches DeepSeek.
   - `did not activate` appears only at run time. The existing post-run guard still fails such a run.
   - In that case the inactive entries are the file tools themselves, so the model can read nothing beyond the prompt.
7. **The DeepSeek adapter takes no session (review F5).** `dsh_command` raises `RunError` if it is ever given a session, and the fake's resume handling is removed. No path can silently reopen persisted state.
8. **Audit:** `DSH_TOOLS` stays `{read, glob, grep}`, so a `working_directory` call would be a disallowed call. Within a fresh run the effective directory cannot change, because the tool is disabled and no prior state exists.

## Non-goals

- Supporting both dsh versions at once.
- Using the model's `effort` levels (`low/high/max`). `--effort` stays refused for DeepSeek.
- Any change to agentic-os. Its runner injects the key, its version gate is `>= 0.2.0-rc.2`, and 705 tests pass on the new binary.
